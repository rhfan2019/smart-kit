# smart-kit：项目目标与范围（v3）

> 本文是给执行方（AI 编码助手）的任务说明，取代同目录的 v1（`项目目标与范围.docx`）和 v2。
> 相对 v2 的变化：对象页进入首期；参考 URL、npm scope、远程仓库已确定。

## 1. 要做什么

做一套**元数据驱动、白盒、可换主题**的 React 组件库，复刻 SAP Fiori Elements 的 List Report 与 Object Page（两者是配套使用的一对页面模板，下文合称「列表-对象页」），但页面由使用者用积木在 JSX 里自己拼。

一句话链路：

```text
OData V4 服务（$metadata + 注解）
   + 外部注解文件（可选）
   + 本地覆盖层（可选）
        ↓ 解析、合并、推导默认值
   规范化元数据模型（下文叫「模型」）
        ↓
   Smart* 积木（筛选栏、表格、字段、表单、值帮助、对象页布局……）
        ↓ 使用者在 JSX 里编排、替换、插入
   列表页 → 对象页
```

三条都是刚性需求，缺一条就不算完成：

1. **注解驱动**：源头是 OData，不是手写配置。手写的部分只用来补充和覆盖。
2. **视觉自由**：不受任何 SAP 主题体系限制，换主题只改 CSS 变量。
3. **白盒可扩展**：页面里任何一块都能被替换，也能在指定位置插入别的元素。

这是个人开源项目，仓库公开，MIT 许可。

## 2. 范围

| 期次 | 内容 |
| --- | --- |
| 首期 | **List Report**，只读：筛选、搜索、排序、分页、列个性化、变体、值帮助、导出 |
| 首期 | **Object Page**，只读：页头与页头 Facet、区块与子区块、锚点导航、表单、子表、子对象页 |
| 首期 | 两者之间的导航：列表行进入对象页、返回时恢复列表状态、对象页可用链接直达 |
| 第二期 | 编辑：直接保存；之后是草稿 |
| 第二期 | 弹性分栏布局（列表和对象页并排显示） |
| 不做 | Overview Page、Analytical List Page、依赖 SAP 平台的功能（磁贴、Launchpad 集成、Key User Adaptation 等） |

列表页和对象页共用同一套元数据、字段、表格和数据层。对象页里的子表就是列表页的表格积木加上父对象上下文，不要做两套。

库不绑定任何路由库。导航通过使用者注入的回调或适配器完成，示例应用里演示一种路由库的接法。

首期不实现编辑，但**编辑是这个库的刚需**，所以首期的设计必须留好接缝，见 6.4。除此之外不为范围外的东西设计泛化能力。

Worklist 是 List Report 去掉筛选栏的变体，积木能拼出来即可，不单独做模板。

## 3. 三个容易理解错的前提

**3.1 协议是标准的，UI 注解不是。**
`$metadata`（CSDL）本身只描述数据结构。"显示哪些列、哪些筛选字段"来自注解，而 UI 注解词汇表（命名空间 `com.sap.vocabularies.UI.v1`）是 SAP 发布的开源规范，不属于 OASIS 标准。OASIS 标准词汇表只有 Core、Capabilities、Measures、Validation、Aggregation 等。

非 SAP 的 OData 服务通常不带任何 UI 注解。所以本库必须在**零 UI 注解**的服务上也能出一个可用的列表页（靠从数据结构推导默认值），再靠覆盖层补全。"不局限于 SAP OData"的验收标准见第 9 节。

**3.2 草稿不是 OData 标准。**
标准 OData 的编辑是 PATCH 加 ETag。草稿（DraftRoot、激活和放弃动作）是 SAP 在标准之上的约定。所以编辑要设计成可插拔的策略，草稿只是其中一种。

**3.3 主要方法是读规范和源码，不是逆向页面。**
设计规范公开，OpenUI5 是 Apache-2.0 开源。但 `sap.ui.comp`（SmartTable 等）和 `sap.fe`（Fiori Elements V4）只随 SAPUI5 发布，是专有许可：**只能读来理解行为，不能复制或改写其代码**。SAP 的字体（72）、图标字体、主题色、CSS 同样不能用。

### 参考应用

```text
https://ui5.sap.com/test-resources/sap/ui/demoapps/demokit/rta/fev4/test/index.html?sap-ui-theme=sap_horizon#product-display
```

这是 SAPUI5 演示套件里的 Fiori Elements V4 应用「Manage Products」，不需要登录。2026-11-14 核对时的情况：SAPUI5 版本 1.154；服务路径 `/sap/opu/odata/sap/SEPMRA_PROD_MAN/`；列表页有 Category、Supplier、Preferred Product 三个筛选字段，产品 205 条，行可进入对象页。

用途和注意事项：

- **用途**：观察每个交互（进入页面、点 Go、排序、滚动加载、打开值帮助、进入对象页、返回）时界面怎么变、发出什么 OData 请求，作为行为规则和查询生成的期望值。
- **请求在 `$batch` 里**：这个应用的数据请求打包在 `$batch` 请求体中，要解开请求体才能看到里面的 `$select`、`$expand`、`$filter`。
- **数据是模拟的**：它没有真实后端，只能用来观察客户端行为，不能用来验证服务端语义。
- **它是 Key User Adaptation 的演示**：界面上与"适配界面"有关的入口不在本项目范围内，忽略。
- **只观察，不搬运**：它的 `$metadata`、注解文件、示例数据、产品图片、样式和图标都属于 SAP，不得存进本仓库。本仓库的测试样本用自己编写的服务和数据。记录下来的请求可以写成"期望的查询形状"，不要整段保存它的响应内容。
- URL 里的 `sap-iapp-state` 参数是某次会话的界面状态，已去掉。
- 访问不了或某个行为观察不到时如实报告，不要凭印象补。

测试用的 OData 服务：

- TripPin 或 Northwind V4（公开，非 SAP，无 UI 注解）。
- 一个本地 CAP 示例服务（带完整 UI 注解）。
- 把它们的 `$metadata` 存成仓库里的固定样本，单元测试不依赖网络。

## 6. 架构要求

### 6.1 分包

```text
packages/core    模型类型、CSDL 与注解解析、合并与默认值推导、
                 查询生成、数据提供者接口、条件模型。纯 TypeScript，不依赖 React 和 DOM
packages/react   Smart* 积木、状态 hook、令牌、文案
apps/demo        示例应用：用积木拼出的列表页
apps/mock        本地测试服务（如需要）
```

依赖方向只能是 `apps → react → core`，用 lint 规则强制。

### 6.2 元数据与注解

- 输入：CSDL XML 和 CSDL JSON 都要能读。
- 注解三来源按优先级合并：本地覆盖层 > 外部注解文件 > 服务自带。再对缺失项推导默认值。
- 解析器优先用现成的。候选是 SAP 开源的 `@sap-ux/edmx-parser` 与 `@sap-ux/annotation-converter`，**采用前核实它们是否存在、许可是否与 MIT 兼容、是否支持 CSDL JSON**，结论写进 ADR。
- 阶段一要产出**注解覆盖矩阵**：每个注解术语标「首期 / 后续 / 不做」，并指向对应的行为规则和测试编号。至少覆盖：`UI.LineItem`、`UI.SelectionFields`、`UI.HeaderInfo`、`UI.PresentationVariant`、`UI.SelectionVariant`、`UI.Facets`（含 `UI.ReferenceFacet` 与 `UI.CollectionFacet`）、`UI.HeaderFacets`、`UI.FieldGroup`、`UI.Identification`、`UI.DataPoint`、`UI.Criticality`、`UI.Hidden`、`UI.Importance`、`Common.Label`、`Common.Text` 与 `UI.TextArrangement`、`Common.ValueList`、`Common.FieldControl`、`Measures.ISOCurrency` 与 `Measures.Unit`、`Capabilities` 的 Filter / Sort / Search / Count / Insert / Update / Delete 限制。
- 模型要有版本号。

### 6.3 数据层

- 定义 `DataProvider` 接口，积木只依赖接口。提供 OData V4 实现和内存实现。
- 网络请求函数由使用者注入，库不处理登录和令牌。
- 按可见列自动计算 `$select` 和 `$expand`，不多取字段。
- 读 Capabilities 注解做能力降级：服务不支持 `$search`、`$count`、某字段不可筛选或排序时，界面隐藏或禁用对应功能，而不是发出会失败的请求。
- `Edm.Decimal` 和 `Edm.Int64` 全程不经过 JS 浮点数。`Edm.Date`、`Edm.DateTimeOffset`、`Edm.TimeOfDay` 分开处理，时区规则写清楚。
- 错误按 OData 错误格式解析，区分页面级和字段级。

### 6.4 为编辑留的接缝

首期不实现编辑，但以下几点首期就要到位，否则第三期要重写：

- 字段组件的类型从一开始就有 `mode: 'display' | 'edit'`。
- 数据提供者接口把读能力和写能力分开定义，写能力首期可以不实现。
- 编辑流程定义成策略接口，至少能容纳两种：直接保存（PATCH 加 ETag）和草稿。
- 在阶段 1.5 用一个最小验证证明接缝是通的：一个字段进入编辑、PATCH、处理 ETag 冲突。验证代码不进首期发布范围。

不要为草稿写一堆没有实现的接口签名。没有被代码验证过的接口，写了也不可信。

### 6.5 骨架与内容

**骨架**按 Fiori 规范来，不做主观改动：区块怎么划分和嵌套、页头的构成、操作放在哪里和何时进溢出菜单、筛选和表格的联动时机、加载 / 空 / 错误 / 无权限的呈现位置、密度档位。理由是用户不需要重新学习。

**内容**可以现代化：色彩、圆角、阴影、边框、字体、间距取值、动效。

判断标准：只影响"看起来如何"的属于内容；影响"在哪里、什么时候出现、如何组织"的属于骨架。两者冲突时骨架优先。

骨架的锁定范围要说清楚：

- **积木内部**的结构是锁定的，例如表格工具栏里标题、动作、个性化按钮的分区和溢出规则。
- **页面级**的编排是开放的，由使用者写 JSX 决定，这是白盒的含义。
- 整页模板（如果提供）只是用公开积木拼出来的示例，不能用任何未公开的内部接口。

### 6.6 扩展机制

需要同时支持"替换"和"插入"：

- **复合组件**：`<SmartTable>` 之下有 `<SmartTable.Toolbar>` 这类具名部件，默认自动渲染，写出来就是覆盖。
- **按 id 寻址**：由模型生成的动态内容（列、筛选字段、动作、对象页的区块和子区块、页头 Facet、表单字段）用 id 定位，覆盖某一个而不影响其余。
- **插入位置**：新增的列、筛选字段、工具栏动作、对象页区块、页头 Facet 可以声明放在某个 id 之前或之后。
- **上下文 hook**：自定义内容通过 hook 拿到数据、选中行、刷新方法、当前筛选条件。
- **类型注册表**：单元格和字段按类型注册渲染器（币种、状态、链接、自定义）。
- **无界面 hook**：筛选状态、列表查询、变体、动作、对象读取、区块滚动跟随各有独立 hook，使用者可以完全不用默认界面。
- 状态同时支持受控和非受控。

某个需求在这套机制里做不到时，向我报告，不要绕开骨架另起一套。

阶段一产出**扩展点清单表**：每个积木有哪些部件、哪些可替换、哪些可插入、注入什么上下文。

### 6.7 主题

三层令牌：

```text
原始值    --sk-yellow-500: #f2c94c            纯色板，无语义
语义      --sk-color-accent: var(--sk-yellow-500)   组件默认引用这一层
组件      --sk-table-header-bg: var(--sk-color-surface-2)   局部微调入口
```

- 组件代码和样式里不出现硬编码的色值、间距、字号，用 lint 检查。
- 换主题只改根元素的 `data-theme`，换密度只改 `data-density`，不重新编译。
- Mantine 和 AG Grid 的主题全部桥接到令牌。
- 图表等需要在 JS 里用颜色的地方，从 CSS 变量读取，主题切换后要跟着变。
- 验收用四个组合：明黄浅色、海军蓝浅色（不是 SAP 蓝）、一套深色、紧凑密度。只换颜色证明不了机制。

阶段一产出**令牌清单表**。

### 6.8 多语言

- 库自带文案集中管理，通过 Provider 注入，默认提供简体中文和英文。组件里不出现硬编码的界面文字，用 lint 检查。
- 元数据里的标签来自服务端，库把当前语言通过 `Accept-Language` 传给服务。
- 数字、日期、币种、单位用 `Intl` 按当前 locale 格式化。
- 布局用逻辑属性（`inline-start` 等），支持从右到左。
- 复数和带参数的文案用占位符，不拼接字符串。

### 6.9 其他质量要求

- 无障碍：WCAG 2.2 AA，表格支持键盘网格导航，axe 检查零违规。
- 状态恢复：从详情返回列表时，筛选、排序、滚动位置和选中行要恢复。
- 性能：服务端分页，长列表虚拟滚动。阶段一给出具体预算（首屏、万行滚动、包体积）。
- 自定义渲染器不能造成 XSS：库不使用 `dangerouslySetInnerHTML` 渲染服务端数据。
- 公开 API：只导出文档里写明的内容，语义化版本，有变更日志。

## 8. 命名与合规

- 包名：`@rhfan2019/smart-kit`（react）与 `@rhfan2019/smart-kit-core`。
- 这个 scope 在 npm 上还没有注册，由我自己去注册。**不要发布到 npm，不要注册账号**；开发期间包只在 monorepo 内部通过 workspace 引用，这不依赖 scope 是否存在。
- scope 将来可能更换。package.json 和 import 语句无法引用常量，所以提供一个改名脚本，而不是 `SCOPE` 常量。
- 组件名 PascalCase，CSS 类名和变量前缀 `sk-`。
- 组件沿用 `SmartTable`、`SmartFilterBar`、`SmartField`、`ValueHelpDialog` 这些名字。它们与 SAPUI5 的控件同名但不是注册商标，这是有意的决定，目的是让熟悉 SAP 的人一眼看懂。写进 ADR。
- **商标词**：`fiori`、`sap`、`sapui5`、`ui5`、`netweaver` 不得作为**独立的词**出现在包名、仓库名、组件名、导出的标识符、CSS 类名里。按词边界判断，`isApplicable`、`disappear` 这类不算。用 CI 脚本检查。
- 以下情况豁免：注解命名空间等协议标识符（如 `com.sap.vocabularies.UI.v1`）、第三方依赖的包名、文档里的描述性引用。
- 文档里引用这些词只用于说明设计来源和兼容性，不暗示授权或隶属。README 开头放声明：

  > SAP、Fiori、SAPUI5 是 SAP SE 的注册商标。本项目与 SAP 无关联，未获任何授权或背书。

- 不使用 SAP 的字体、图标、主题色和 CSS。示例数据自己编，不取自任何真实系统。
- 库的代码里不出现任何业务实体名，用测试检查。

## 9. 怎么证明做对了

验收不靠我或你的主观判断，靠下面这些：

1. **多后端**：同一套端到端用例在带注解的 CAP 服务和不带注解的 TripPin（或 Northwind）上都通过。
2. **服务器接受**：生成的每一类查询都被真实 OData 服务接受并返回正确结果。
3. **差分对照**：自己编写一个结构和注解与参考应用同类的产品管理服务，对比参考应用与本库在同类操作下的界面构成（列、筛选字段、页头、区块）和查询形状（`$select`、`$expand`、`$filter`、`$orderby`、分页），差异逐条解释。
4. **自举**：示例的列表页和对象页只用公开导出的积木拼成；换一个实体再拼一套页面时，不改库代码。
5. **扩展**：示例里演示四种用法：替换一个块；在列表页的指定位置插入一列和一个工具栏动作；在对象页的指定位置插入一个自定义区块；完全不用默认界面只用 hook。
6. **导航**：从列表进入对象页再返回，筛选、排序、滚动位置恢复；对象页的链接复制到新标签页能直接打开；子对象页可进入和返回。
7. **主题**：四个组合各有截图回归；无硬编码的 lint 通过；文字对比度达标。
8. **多语言**：切换到英文后界面没有残留中文；切到一种从右到左的语言后布局镜像正确。
9. **机器检查全绿**：类型检查（strict）、lint、单元测试、端到端测试、axe、包体积，全部在 CI 上跑。
10. **可追溯**：注解覆盖矩阵里标「首期」的每一项，都能指到一条通过的测试。
